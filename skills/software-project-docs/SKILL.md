# 软件研发项目管理过程文档

为软件研发项目生成**可直接评审归档**的过程文档（DOCX），覆盖立项、规划、设计、执行监控、收尾 18 类；也支持生成带示例与填写说明的**模板**、把**已有文档重构/拆分/合并**为新文档，以及**补齐**项目缺失的过程文档。本技能同时约束内容边界、排版规范和版本修订方式。

## 先读：八条硬性规则

1. **先确认，再生成。** 每次任务先调用 `ask_user_question` 确认要生成哪些文档、正式还是模板、新建还是修订。不得默认全量生成，不得揣测清单。
2. **内容只来自项目资料。** 不编造客户名、人名、金额、日期、指标、评审结论、签字。资料缺失时在正文用 `【待确认：…】` 占位，并登记到该文档附录的"待确认事项"表。
3. **正文不出现过程性说明。** 不写"本次修订了…""根据您的要求…""由 AI 生成"等任何过程描述或 AI 痕迹；文档里只有正式内容和一张正式的《修订记录》表。
4. **模板模式必须带说明与示例。** 每个需要填写的章节配 `【填写说明】`（楷体斜体）和一段自洽的示例（楷体斜体），说明写"填什么、写到什么粒度"，不写空话。
5. **每次修订都升版本、出新文件、保留旧版。** 版本号、页眉、封面、修订记录表、文件名五处必须一致。
6. **交付前必须自检。** 运行 `scripts/check_docx.py`，`errors` 清零才算完成；warnings 要逐条判断。
7. **重构旧文档时旧文件只读。** 只抽取事实、不搬用旧格式与旧编号；每条事实带来源，不采用的内容必须列清单，缺失内容转 `【待确认】`。重构产物是新文件，独立编号体系。
8. **不越界。** 只写该文档职责范围内的章节；跨文档内容用引用说明，不复制粘贴、不扩写成为另一份文档的内容。

## 工作流

### 第 0 步：加载依赖

先 `skill` 加载 `office-docx`（写 DOCX 的基础规范）。需要 PDF 或渲染时再加载 `office`。本技能自带构建库，不需要另写排版代码。

### 第 1 步：交互确认（强制）

按 `references/workflow.md` 的模板一次性问清六件事：

- **工作模式**：新建 / 重构（同类型重写）/ 拆分（一份变多份）/ 合并（多份合一）/ 补齐（生成缺失文档），可组合；
- **文档清单**：18 类多选（见 `references/catalog/overview.md`），并给出"核心 5 份"的推荐组合；
- **模式**：正式文档 / 模板（含示例与填写说明）；
- **版本**：新建 `V1.0`，还是修订既有文档（需要旧文件和内容源路径）；
- **项目信息**：项目名称、项目编号、客户/建设单位、编制人、审核人、批准人、密级、文档日期；
- **输出位置与资料**：输出目录，以及可用的项目资料（文件、目录或口述要点）。

用户跳过某项时按下表取默认值，并在回复中说明所取默认值：

| 项目 | 默认值 |
|---|---|
| 工作模式 | 新建 |
| 文档清单 | 不生成，继续询问 |
| 模式 | 正式文档 |
| 版本 | V1.0 |
| 密级 | 内部 |
| 日期 | 当天 |
| 输出目录 | `<工作区>/docs/` |

### 第 2 步：资料盘点

读取用户提供的文件（需求、会议纪要、合同、原型、旧版文档等），输出一张"资料—文档"对照表：每份文档需要哪些输入、已具备哪些、缺哪些。缺口先请用户补，补不了就转成 `【待确认】`，不要自行发挥。

### 第 3 步：逐份生成

每份文档走同一条流水线：

1. 在 `docs/_source/` 下写内容源 `<文档代码>_<版本>.md`（受控 Markdown，见下节）；
2. 构建：`python -B <技能目录>/scripts/build.py <内容源> -o <输出.docx>`；
3. 自检：`python -B <技能目录>/scripts/check_docx.py <输出.docx>`；
4. 按 `errors` 修正内容源并重建，直到通过；
5. 需要视觉确认时用 `office_render` 查看首页、目录页与一张表格页。

内容严谨度按 `references/content-rules.md` 执行，章节骨架照 `references/catalog/` 对应该文档的部分，不得增删一级章节（确有需要时在回复中说明理由）。

### 第 4 步：修订（已有文档）

按 `references/revision.md`：

1. 读旧版内容源（没有时先从 DOCX 还原章节结构，只还原不使用反编译）；
2. 只改需要改的章节，保持其余文字不动；
3. 版本号按规则递增（结构调整 → 主版本；内容修订 → 次版本）；
4. 在 front matter 的 `revisions` 追加一行，写清"修订了什么"，不写过程；
5. 重建为**新文件**，旧文件原样保留，更新 `docs/_manifest.json`。

### 第 5 步：重构与补齐（已有文档）

用户拿已有文档要求"整理成规范文档""拆成几份""合成一份"或"还缺哪些文档"时走这条路径，完整规则见 `references/reconstruct.md`。

1. **盘点**：`python -B <技能目录>/scripts/inventory_docs.py <输入目录> -o docs/_source/inventory.json`，给每份文档打标签（可用／需重写／仅供参照／不可用）。
2. **事实台账**：按九个维度抽取事实，每条带来源文件与章节，置信度分高／中／低；低置信度一律转 `【待确认】`。
3. **冲突不裁决**：多来源不一致时列冲突表交用户决定，不自行取舍。
4. **映射与缺口**：画"来源→目标章节"矩阵；缺口分未覆盖／来源缺失／来源过时／来源矛盾四类分别处理。
5. **重建**：按统一规范生成新文件，重排章节、表图、需求与用例编号，统一术语，重算交叉引用；旧文件保持只读。
6. **不丢内容**：未采用的内容列成清单随交付回复给出；追溯信息写进 `_manifest.json` 的 `sources`，不写进正文。
7. **补齐**：按 `references/catalog/overview.md` 的阶段矩阵判断该阶段缺哪些文档，只补缺失与需重构的，按依赖顺序生成。

### 第 6 步：交付

用 `present` 交付 DOCX；回复中给出：生成清单、每份的版本与路径、自检结论、待确认事项数量、下一步建议；重构任务另附"未采用清单"与"冲突待裁决项"。不要粘贴整篇文档正文。

## 内容源格式（受控 Markdown）

front matter 与正文块如下，语法细节与完整示例见 `assets/content-format.md` 和 `assets/sample-srs.md`。

```markdown
---
project: 智慧园区综合管理平台
project_code: YQ-2026-001
doc_code: YQ-2026-001-REQ-SRS
title: 软件需求规格说明书
version: V1.0
date: 2026-11-21
classification: 内部
issuer: 某某科技有限公司
author: 张三
reviewer: 李四
approver: 王五
mode: template            # formal | template
layout: full              # full（封面+目录）| brief（短文档：标题块+修订记录）
revisions:
  - V1.0 | 2026-11-21 | 张三 | 首次发布
---

# 引言            → 自动编号「1 引言」
## 编写目的        → 「1.1 编写目的」
表: 功能清单 || 12,26,14,16,10,22   → 表号「表3-1」+ 列宽比例
| 编号 | 功能名称 | … |
图: 系统架构 || assets/arch.png || 12
:::fill 填写说明文字（模板模式）
:::example 示例文字（模板模式）
# 附录 A 待确认事项   → 附录不参与章节编号，表号变为「表A-1」
```

构建库自动完成：封面、修订记录表、目录域、分节页码、页眉、标题编号、表图编号、表格底纹与重复表头。

## 命令速查

```powershell
# 盘点已有文档（重构/补齐前）
python -B "<技能目录>\scripts\inventory_docs.py" "旧资料目录" -o "docs\_source\inventory.json"

# 构建
python -B "<技能目录>\scripts\build.py" "docs\_source\YQ-2026-001-REQ-SRS_V1.0.md" -o "docs\YQ-2026-001-REQ-SRS_V1.0.docx"

# 自检
python -B "<技能目录>\scripts\check_docx.py" "docs\YQ-2026-001-REQ-SRS_V1.0.docx"
```

Python 用 `load_workspace_dependencies` 返回的解释器；`-B` 不可省略（技能目录只读，禁止写 `__pycache__`）。

## 边界

- 不做商务报价、法务条款、涉密等级判定；这些内容缺失时一律占位并提示用户补充。
- 不替用户下结论（验收是否通过、风险等级、里程碑是否达成），只按资料陈述并标注依据。
- 不生成与所选文档无关的章节；不把一份文档写成另一份的扩写。
- 图表只使用用户提供的图片或明确的数据；没有数据时给表格骨架 + `【待确认】`，不虚构数字。
