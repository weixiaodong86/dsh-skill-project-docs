# 文档重构与补齐

重构不是"换个模板重排"，而是把旧文档拆成**事实单元**，再按目标文档的章节结构重新组织。补齐则是在同一套事实台账上，判断哪些过程文档还缺、缺什么内容。

## 1. 五种工作模式

| 模式 | 适用 | 输入 | 输出 | 版本 |
|---|---|---|---|---|
| 新建 | 从零写文档 | 项目资料 | 新文档 | V1.0 |
| 重构 | 旧文档格式乱、结构不达标，内容仍有效 | 一份旧文档 | 同类型新文档 | V1.0（新建编号体系） |
| 拆分 | 一份综合文档含多类内容（如"实施方案"里混着需求、计划、测试） | 一份大文档 | 多份过程文档 | 各 V1.0 |
| 合并 | 多份零散文档要合成一份正式文档 | 多份文档 | 一份文档 | V1.0 |
| 补齐 | 项目某阶段缺文档 | 已有文档集 + 阶段 | 缺失文档 | 各 V1.0 |

模式可组合：先拆分再补齐是常见路径。**旧文件一律只读**，重构产物是新文件。

## 2. 六步流程

### R0 确认范围

问清四件事，缺一不可：

1. 输入是哪些文件（路径/目录），有没有不能用的（涉密、过期、别的项目残留）；
2. 要哪种模式，或"先拆分再补齐"；
3. 目标文档清单（按 `catalog/overview.md`）；
4. 旧文档如何处理（默认只读保留，可另存归档目录）。

### R1 盘点

用 `scripts/inventory_docs.py` 扫描输入目录，得到一份盘点表：

```powershell
python -B "<技能目录>\scripts\inventory_docs.py" <输入目录> -o <工作区>\docs\_source\inventory.json
```

脚本输出每份文档的：文件名、格式、字数、标题层级、表格数、最后修改时间。据此给每份文档打标签：

| 标签 | 判定 | 用法 |
|---|---|---|
| 可用 | 结构完整、内容在本项目范围内 | 作为事实来源 |
| 需重写 | 内容有效但结构/格式不达标 | 重构的对象 |
| 仅供参照 | 模板、他项目文档、过期版本 | 不抽取事实，只参考章节 |
| 不可用 | 涉密、损坏、无来源说明 | 剔除并记录原因 |

### R2 事实台账

按维度抽取，每条事实一行，必须带来源：

| 编号 | 维度 | 事实内容 | 来源文件 | 来源章节 | 置信度 |
|---|---|---|---|---|---|
| F-001 | 范围 | 一期覆盖企业入驻、缴费、报修 | 需求 V0.3 | 1.2 | 高 |
| F-002 | 里程碑 | 2027-03-31 上线试运行 | 项目周报 202611 | 3.1 | 中 |

抽取维度固定为九类：范围、需求、进度与里程碑、组织与角色、指标与约束、风险、成本、接口与集成、验收标准。

置信度判定：

- **高**：正式文档中的明确陈述；
- **中**：周报、纪要等过程记录中的陈述；
- **低**：口头传达、单处提及且无佐证 —— 写入文档时必须标 `【待确认】`。

同一事实多来源不一致时**不合并、不取舍**，列入冲突表交用户裁决：

| 编号 | 事实 | 来源 A | 来源 B | 差异 | 裁决 |
|---|---|---|---|---|---|
| C-001 | 并发用户数 | 需求 V0.3：500 | 立项报告：800 | 目标值不一致 | 待裁决 |

### R3 映射与缺口

画一张"来源 → 目标章节"矩阵，同时暴露缺口：

| 目标文档 | 目标章节 | 来源 | 状态 |
|---|---|---|---|
| 需求规格说明书 | 3.1 功能清单 | 需求 V0.3 第 2 章 | 有来源 |
| 需求规格说明书 | 4.1 性能需求 | 无 | 缺口 |
| 项目管理计划 | 5.2 进度计划 | 周报 3.1 | 有来源（中置信） |

缺口分四类，处理方式不同：

| 缺口类型 | 处理 |
|---|---|
| 未覆盖：目标章节在来源里完全没有 | 写 `【待确认：…】` 并登记附录；能推断的写"按…推算"并标依据 |
| 来源缺失：应有但没提供文件 | 先问用户要，要不到按上一条处理 |
| 来源过时：内容与当前事实不符 | 以最新来源为准，旧值记入冲突表 |
| 来源矛盾：两处说法不同 | 不裁决，列冲突表，等用户确认 |

### R4 生成

- **按统一规范重建**，不继承旧文档的样式、编号、页眉；
- 事实重写成正式陈述句，不整段搬移原文；
- 编号体系重排：章节、表、图、需求编号、用例编号全部按新文档重新编号；
- 术语统一：旧文档的不同叫法收敛到术语表的一种，其余在术语表里注明"又称"；
- 交叉引用重算：旧文档的"见第 3.2 节"在拆分后要指向新文档的新章节；
- 旧文档中出现但新文档用不到的内容，进"未采用清单"，不静默丢弃。

### R5 追溯与交付

正文**不写**"本文档重构自…"之类的说明（属于过程信息）。追溯信息放在项目内的 `docs/_manifest.json`：

```json
{
  "doc_code": "YQ-2026-001-REQ-SRS",
  "version": "V1.0",
  "sources": [
    { "file": "旧资料/需求说明书V0.3.docx", "sha256": "…", "sections": ["2", "3.1"] }
  ]
}
```

## 3. 未采用清单

重构最容易出的问题不是写错，而是**悄悄丢内容**。每份重构产物都附一张内部清单（不进正文）：

| 序号 | 内容摘要 | 来源 | 未采用原因 | 建议 |
|---|---|---|---|---|
| 1 | 二期规划的三项功能 | 立项报告 3.4 | 超出本期范围 | 转入后续规划 |
| 2 | 旧接口地址 10.1.2.3 | 旧设计 5.2 | 已下线 | 删除 |
| 3 | 两种不同的验收口径 | 需求 7.1 / 会纪要 2 | 互相矛盾 | 待裁决 |

清单随交付回复给用户，让"没写进去的东西"是可见的。

## 4. 拆分与合并的额外规则

**拆分**（一份 → 多份）：

- 先列出原文档的章节，标注每章归属的目标文档；
- 归属为"多份共用"的章节（如术语、参考资料）复制进各文档并各自维护，不写"见另一份文档"；
- 拆分后每份文档自成体系：有自己的范围、术语、追溯。

**合并**（多份 → 一份）：

- 先做章节去重表：同名章节只保留一份，内容合并后去重；
- 版本号取被合并文档中的最高版本 +1 个主版本；
- 合并后的文档必须能独立评审，不依赖被合并的原文件。

## 5. 补齐的判定

按 `catalog/overview.md` 的阶段矩阵判断"这个阶段至少该有哪些文档"，再对照盘点结果：

1. 列出该阶段必需文档；
2. 标出已有（可用的）、需重构的、完全缺失的；
3. 只补**缺失**与**重构**两类，不重复生成已有的合格文档；
4. 补齐顺序按依赖：上游先于下游。

## 6. 交付报告

```
重构/补齐完成：
- 输入 12 份，可用 7 份、需重写 3 份、仅供参照 2 份
- 产出 5 份：需求规格说明书 V1.0（重构）、概要设计 V1.0（补齐）、…
- 事实台账 46 条，其中【待确认】3 条
- 冲突 2 项待裁决：并发用户数、验收口径
- 未采用 4 项，见清单
- 旧文件未改动，位于原目录
```

## 7. 常见问题

| 情况 | 处理 |
|---|---|
| 旧文档是别的项目的模板残留 | 整段剔除，只在盘点表记录"他项目残留" |
| 旧文档含未公开数据（客户名、金额） | 保留原文但不扩散；文档密级按用户要求标注 |
| 旧文档只有 PDF/图片 | 先转文本再抽取；图片里的表格需人工确认后录入 |
| 用户要求"照旧文档原样出一版" | 明确这是"转格式"而非"重构"，只需重排版，不改内容与结构 |
| 重构后与旧文档结论不一致 | 这是正常结果，把差异写进交付报告，不悄悄改旧文档 |
