# 内容规范与边界

## 1. 事实来源分级

按可信度使用，越靠上越优先：

| 级别 | 来源 | 写法 |
|---|---|---|
| A | 用户提供的正式资料（合同、需求文档、评审意见、系统截图、台账） | 直接陈述，必要时注明来源文件 |
| B | 用户在对话中的明确说明 | 直接陈述 |
| C | 行业通行做法、标准条款 | 写成"按行业通行做法…"或"参照 GB/T 8567…"，不写成项目事实 |
| D | 推测 | **不使用**。转为 `【待确认】` 或删除该句 |

## 2. 禁止编造

以下内容没有 A/B 级来源时一律不得出现具体值：

- 客户名称、建设单位、供应商、人名、职务、联系方式；
- 金额、工期、人数、并发量、响应时间、可用性指标；
- 测试通过率、缺陷数、验收结论、评审结论、签字与日期；
- 合同编号、立项批复号、等保等级、备案号。

缺失时写：`【待确认：并发用户数指标，责任人 李四，2026-11-30 前确认】`，并在附录"待确认事项"表中登记同一行。

## 3. 占位符规范

| 场景 | 写法 |
|---|---|
| 缺数值 | `【待确认：日均订单量】` |
| 缺责任人 | `【待确认：责任人】` |
| 整章未纳入本次范围 | 保留标题，正文写`【本次未编写】` |
| 图片未提供 | 保留图题，图位写`［图片缺失：系统架构图］` |

占位符必须满足：**可定位**（写明缺什么）、**可闭环**（有责任人或确认时点）、**可统计**（附录表与正文一致）。

## 4. 不扩散：每份文档的边界

- 只写该文档职责内的章节（见 `catalog/`）。需求文档不写数据库表结构；设计文档不复述需求条目；测试报告不写项目总结。
- 需要引用其他文档时写"详见《××》第 x 节"，不复制其内容。
- 不加入与项目无关的方法论介绍、产品宣传、团队介绍。
- 单份文档的篇幅与项目规模匹配：中小型项目正文 10–25 页，不为凑页数扩写。

## 5. 语言与语气

| 要求 | 说明 |
|---|---|
| 人称 | 第三人称陈述；不出现"我们""您""我" |
| 时态 | 陈述现状与要求，不用"将要""打算" |
| 句式 | 短句，一句一个判断；避免连续三个以上定语 |
| 术语 | 首次出现写全称并括注缩写，之后统一用缩写 |
| 数字 | 阿拉伯数字；日期 `YYYY-MM-DD`；区间用"～"；单位用法定单位并在首次出现时说明 |
| 程度词 | 少用"非常""极大""显著"，用可验证的表述 |

## 6. 过程性说明与 AI 痕迹（禁止）

正文中不得出现下列任何一类：

- 修订过程："本次修改了 3.2 节""相比上一版补充了…""本版主要变化…"；
- 交互痕迹："根据您的要求""已按您的意见调整""如需修改请告知"；
- AI 痕迹："由 AI 生成""本文档由助手整理""（AI 生成）"；
- 自述："本文档编写仓促""部分内容待完善"。

修订信息只出现在两个地方：**《修订记录》表**（正式内容）与**项目内的版本登记文件**（`_manifest.json`，不随文档交付）。

修订记录只写结论，不写过程：

| 正确 | 错误 |
|---|---|
| `补充 4.2 性能指标与验证方式` | `根据评审意见，我把原来空着的 4.2 补上了，之前漏了` |
| `调整验收标准表述，与合同附件一致` | `本次修改是应张总要求改的` |

## 7. 正式模式 vs 模板模式

| 维度 | 正式文档 | 模板 |
|---|---|---|
| 章节 | 完整填写 | 完整保留骨架 |
| 填写说明 | 无 | 每章必须有一处 `:::fill` |
| 示例 | 无 | 每章至少一段 `:::example`（确无示例时在说明中注明） |
| 占位符 | 尽量少，缺资料才用 | 允许较多，但必须可定位 |
| 语言 | 可直接评审 | 说明用祈使句指导填写，示例用陈述句 |

模板的填写说明写"填什么、写到什么粒度、依据什么资料"，例如：

```
:::fill 说明本系统的建设目标与业务价值，控制在 150 字以内；依据项目建议书第 2 章。
:::
```

不要写成"请在此处填写相关内容"。

## 8. 一致性检查（写完自查）

- 术语表与正文用词一致；
- 章节号、表号、图号与正文引用一致；
- 同一数据在不同章节取值一致；
- 附录"待确认事项"与正文占位符一一对应；
- 修订记录版本号、页眉版本号、文件名版本号一致。

## 10. 重构时的保真规则

重构可以改结构、改措辞、改编号，**不能改事实**。

| 可以变 | 不可以变 |
|---|---|
| 章节顺序与层级 | 事实的取值、结论、责任主体 |
| 表述方式与术语统一 | 数据的口径（除非来源更新并注明） |
| 编号体系（章节、表、图、需求、用例） | 需求条目的含义与优先级 |
| 表格的列组织 | 表格里的数值 |
| 旧文档的"建议/设想"标签 | 把"建议"写成"已确定" |

具体要求：

- **事实单元不增不减**：旧文档的每条事实在新文档里要么出现、要么进"未采用清单"，不允许静默消失。
- **待定仍是待定**：旧文档写"暂定""待定""拟"的内容，新文档保持待定并转 `【待确认】`，不得补成确定值。
- **结论随来源**：旧文档的结论若没有新依据，保持原结论；若用户提供了新依据，按新依据写并记录来源变化。
- **不借机扩写**：重构不是补充材料的机会，缺的内容走"补齐"模式单独确认。
- **数字与日期不重算**：只搬运，不重新计算；确需换算时注明换算依据。

## 11. 常见缺陷

| 缺陷 | 修正 |
|---|---|
| 章节标题写成"其他""附录"等无信息标题 | 改为具体内容名 |
| 表格只有表头 | 补示例行或 `【待确认】` 行 |
| 需求条目缺少验收标准 | 每条需求补"验收方式"列 |
| 风险只列不评 | 补概率、影响、等级、应对、责任人 |
| 结论章节写"项目成功完成" | 改为有依据的达成情况对照 |
