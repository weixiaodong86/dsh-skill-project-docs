# 工作流与交互脚本

## 1. 交互确认：一次问清

用一次 `ask_user_question` 提四个问题（模式 + 清单多选 + 文档形态 + 版本），项目信息用第五问的"自定义回答"收集。问题要短，选项要自解释。

### 问题零：工作模式

| label | 说明 |
|---|---|
| 新建文档（推荐） | 从项目资料直接写新文档 |
| 重构已有文档 | 旧文档内容有效但结构/格式不达标，重写为规范版 |
| 拆分一份文档 | 一份综合文档拆成多份过程文档 |
| 合并多份文档 | 多份零散文档合成一份正式文档 |
| 补齐缺失文档 | 按项目阶段找出缺哪些文档并生成 |

模式可叠加（"先拆分再补齐"），在自定义回答里说明即可。

### 问题一：文档清单（`multi_select: true`）

选项按下表给出，label 用"编号 + 名称"，description 写一句"什么时候要它"。**首选项放最常用的组合**，并把推荐标在 label 上。

| # | label | description |
|---|---|---|
| 1 | ① 项目管理计划 | 立项后第一份总纲，范围/进度/成本/质量/风险全覆盖 |
| 2 | ② 软件需求规格说明书 | 需求确定后编写，是设计、测试、验收的依据 |
| 3 | ③ 概要设计说明书 | 架构与技术选型确定后编写 |
| 4 | ④ 详细设计说明书 | 模块级设计与接口约定 |
| 5 | ⑤ 测试计划 | 测试启动前编写，定义范围、策略、准入准出 |
| 6 | ⑥ 测试报告 | 测试执行结束、验收前编写 |
| 7 | ⑦ 验收报告 | 交付验收时编写，含结论与签字 |
| 8 | ⑧ 项目总结报告 | 结项时编写，含目标达成与经验教训 |
| 9 | ⑨ 立项报告 | 项目启动前编写，含背景、方案、投资、结论 |
| 10 | ⑩ 质量保证计划 | 质量目标与评审/审计安排 |
| 11 | ⑪ 配置管理计划 | 配置项、基线、变更控制 |
| 12 | ⑫ 风险管理计划 | 风险识别、分析、应对与监控机制 |
| 13 | ⑬ 风险登记册 | 项目执行期的风险台账 |
| 14 | ⑭ 项目周报/月报 | 周期性进度与问题报告 |
| 15 | ⑮ 会议纪要 | 评审会、例会、专项会记录 |
| 16 | ⑯ 变更请求单 | 范围/进度/成本变更的申请与审批 |
| 17 | ⑰ 部署上线方案 | 上线前的部署、迁移、回滚与值守安排 |
| 18 | ⑱ 用户手册 | 面向最终用户的操作说明 |

推荐组合（写进问题描述，减少用户决策成本）：

- **核心 5 份**：②需求规格、③概要设计、⑤测试计划、⑥测试报告、⑦验收报告；
- **管理 4 份**：①项目管理计划、⑭周报/月报、⑮会议纪要、⑯变更请求单；
- **全套 18 份**：仅当用户明确要建整套文档体系。

### 问题二：模式

| label | 说明 |
|---|---|
| 正式文档（推荐） | 直接写可评审的内容，不含填写说明 |
| 模板 | 每章给【填写说明】与示例，供他人填写 |

### 问题三：版本

| label | 说明 |
|---|---|
| 新建 V1.0 | 首次生成 |
| 修订已有文档 | 需要提供旧文件或旧内容源路径，按 `revision.md` 升版本 |

### 问题四：项目信息（不给选项，等自定义回答）

> 请提供项目信息（缺项可留空，我会用【待确认】占位）：项目名称、项目编号、建设单位、编制人、审核人、批准人、密级（公开/内部/秘密/机密）、文档日期、输出目录。

## 2. 资料盘点

读完资料后，先给用户一张表再动笔：

| 目标文档 | 必需输入 | 已具备 | 缺口 | 处理方式 |
|---|---|---|---|---|
| 需求规格说明书 | 需求清单、业务调研、接口清单 | 需求清单 | 接口清单 | 【待确认】+ 附录登记 |

缺口处理顺序：**先问一次 → 用户无法提供则占位 → 占位必须登记**。不要连续追问同一件事超过一次。

## 3. 重构与补齐

触发说法："把这份旧文档整理成规范版""拆成需求、设计、测试三份""这几份合成一份""看看还缺哪些文档""按我们的模板重出一版"。

1. **确认**：模式、输入文件、旧文件能否使用（涉密/过期/他项目残留）、旧文件是否保留（默认只读保留）；
2. **盘点**：`python -B <技能目录>/scripts/inventory_docs.py <输入目录> -o docs/_source/inventory.json`，给每份文档打标签（可用／需重写／仅供参照／不可用）；
3. **事实台账**：按九维度抽取，每条带来源与置信度；低置信度转 `【待确认】`；
4. **冲突与缺口**：冲突表请用户裁决，缺口表请用户确认补法；不自行取舍；
5. **生成**：按统一规范重建新文件，重排编号、统一术语、重算交叉引用；旧文件不动；
6. **交付**：产物 + 未采用清单 + 冲突/缺口 + 追溯写入 `_manifest.json`。

完整规则（含拆分/合并的额外要求）见 `reconstruct.md`。

## 4. 多文档编排

- 按依赖顺序生成：立项 → 计划 → 需求 → 设计 → 测试计划 → 测试报告 → 验收 → 总结；管理与记录类文档（周报、纪要、变更单、风险登记册）随项目周期穿插。
- **一次只生成一份**，每份完成后给一行进度（"②需求规格说明书 V1.0 已生成，自检通过，待确认 3 项"），再继续下一份。
- 后一份文档引用前一份时写清章节号（"详见《软件需求规格说明书》3.2 节"），不复述其内容。
- 全部完成后给一张总表：文档、版本、路径、自检结果、待确认项数量。

## 5. 生成后的回复格式

```
已生成 3 份文档（正式版）：
1. 软件需求规格说明书 V1.0 — docs/xxx.docx — 自检通过，待确认 3 项
2. 概要设计说明书 V1.0 — docs/yyy.docx — 自检通过
3. 测试计划 V1.0 — docs/zzz.docx — 自检通过，待确认 1 项
说明：测试计划中的环境地址与测试数据未提供，已占位并登记在附录 A。
```

## 6. 修订的触发与识别

以下说法都算修订请求，先确认对象与改动范围，再动手：

- "把验收报告的安全章节补上""需求 3.2 的验收标准改成…"；
- "根据这份评审意见改一版"（评审意见是修订依据）；
- "上一版哪里不对，重出一版"（先定位差异，再确认是否整篇重写）。

修订时**不新建章节结构**，除非用户明确要求调整结构；结构调整按主版本处理。

## 7. 异常处理

| 情况 | 处理 |
|---|---|
| 用户只要一部分章节 | 只写要求的章节，其余保留标题并标 `【本次未编写】`，不要删章节 |
| 资料互相矛盾 | 列出矛盾点让用户裁决，未裁决前不合并 |
| 构建报错 | 检查内容源语法（表格列数、`||` 分隔、图片路径），修内容源而不是改构建库 |
| 自检 error | 按 code 修正：`heading` 改标题层级、`caption` 补表题、`style` 去掉规范外样式、`version` 对齐页眉与封面 |
| 图片缺失 | 保留图题与占位提示，告知用户补图后重建 |
| 用户要求改动版式 | 先说明将偏离统一规范，用户确认后再改 `assets/docx_kit.py` 顶部常量 |
