# 设计与执行阶段文档骨架

本文件给出 ⑧–⑮ 的章节骨架。设计与执行类文档最容易越界：设计文档不要复述需求，报告类文档不要写计划。

---

## ⑧ 概要设计说明书（DES-HLD）

**目的**：确定系统架构、模块划分、接口与数据总体方案，作为详细设计的输入。
**必备表格**：模块清单、接口清单、技术选型对照表、部署节点表。

```
1 引言
  1.1 编写目的
  1.2 范围
  1.3 术语与缩略语
  1.4 参考资料
2 总体设计
  2.1 设计目标与原则
  2.2 系统架构
  2.3 技术选型
  2.4 部署架构
  2.5 逻辑分层
3 模块划分
  3.1 模块清单
  3.2 模块职责
  3.3 模块间关系
4 接口设计
  4.1 外部接口
  4.2 内部接口
  4.3 接口规范
5 数据设计
  5.1 概念数据模型
  5.2 主要数据表
  5.3 数据流
6 安全设计
  6.1 身份认证
  6.2 权限模型
  6.3 数据安全
  6.4 审计日志
7 非功能设计
  7.1 性能设计
  7.2 可用性设计
  7.3 扩展性设计
8 运行与维护设计
  8.1 部署方式
  8.2 监控与告警
  8.3 备份与恢复
附录 A 模块清单
附录 B 待确认事项
```

**要点**

- 技术选型写"选了什么、为什么、放弃了什么"，纯罗列技术栈等于没写；
- 模块职责一句话说清"负责什么、不负责什么"；
- 架构图必须有图题，图内元素与模块清单的编号一致；
- 需求追溯：每个模块标注实现的需求编号，不写"实现全部功能"。

**常见缺陷**：把架构图画成部署图；接口只给名字不给协议与数据格式；安全设计写"采用加密"。

## ⑨ 详细设计说明书（DES-LLD）

**目的**：把概要设计细化到可实现、可编码、可单测的粒度。
**必备表格**：模块—类—方法清单、接口参数表、数据库表结构表、错误码表。

```
1 引言
2 模块详细设计
  2.x 模块名称（每个模块一节，按此结构重复）
    功能描述 / 类与函数 / 处理流程 / 异常处理
3 接口详细定义
  3.1 接口清单
  3.2 请求与响应定义
  3.3 错误码
4 数据库详细设计
  4.1 表结构
  4.2 索引设计
  4.3 视图与存储过程
5 界面设计
6 关键算法与业务规则
7 错误处理与日志
附录 A 表结构清单
附录 B 待确认事项
```

**要点**

- 表结构给出字段名、类型、长度、是否必填、默认值、说明、索引，缺一列就不算详细设计；
- 处理流程描述"输入→校验→处理→落库→返回"的顺序，不写代码；
- 错误码统一编码规则（模块段 + 序号），与接口定义一致；
- 关键算法写清边界条件与复杂度，涉及金额、计费、权限的必须给判定规则。

**常见缺陷**：详细设计写成伪代码堆砌；表结构与概要设计的数据模型对不上；异常分支缺失。

## ⑩ 项目周报/月报（RPT-STATUS）

**目的**：周期性同步进度、问题、风险与下期安排，供决策与协调。
**必备表格**：本期完成清单、里程碑进展表、问题与风险表、下期计划表。

```
1 报告概述
  1.1 报告周期
  1.2 编制人
  1.3 数据截止时间
2 本期完成情况
  2.1 里程碑进展
  2.2 交付物完成情况
  2.3 工作量投入
3 进度与偏差分析
4 问题与风险
  4.1 待解决问题
  4.2 风险状态
  4.3 需协调事项
5 资源与成本（按需）
6 下期计划
7 需决策事项
附录 A 待确认事项
```

**要点**

- 计划 vs 实际并列，偏差用百分比或天数表达；
- 问题写"现象 + 影响 + 责任人 + 期望解决时间"，不写"存在一些问题"；
- 需决策事项单独列，写清"决策什么、不决策的后果、最晚决策时间"；
- 数据与上期报告可比，口径变了要说明。

## ⑪ 会议纪要（RPT-MIN）

**目的**：固定会议结论与待办，避免"会开了、事没人做"。
**必备表格**：参会人员表、待办事项表（事项/责任人/期限/状态）。

```
1 会议基本信息
  1.1 会议名称
  1.2 时间与地点
  1.3 主持人与记录人
  1.4 参会人员
2 会议议题
3 讨论要点
4 决议事项
5 待办事项
6 附件
```

**要点**

- 讨论要点按议题分条，写观点与分歧，不写流水账；
- 决议必须可执行，写"由谁在什么时间前完成什么"；
- 待办事项与决议一一对应，编号连续；
- 未达成一致的事项写"未决"，并注明下次讨论时间，不替会议下结论。

## ⑫ 变更请求单（CHG-REQ）

**目的**：让每一处变更都经过评估与审批，留下影响分析。
**必备表格**：变更基本信息表、影响分析表、审批签署表、验证记录表。

```
1 变更基本信息
  1.1 变更编号
  1.2 提出人与提出日期
  1.3 变更类型（范围/进度/成本/技术/其他）
2 变更内容
  2.1 现状
  2.2 变更后
  2.3 变更原因
3 影响分析
  3.1 对范围的影响
  3.2 对进度的影响
  3.3 对成本的影响
  3.4 对质量的影响
  3.5 对风险的影响
4 变更方案
  4.1 实施方案
  4.2 工作量估算
  4.3 回退方案
5 评审意见
6 审批结论
7 实施与验证
附录 A 待确认事项
```

**要点**

- 影响分析五要素缺一不可，没有影响就写"无影响"并给判断依据；
- 工作量估算写人天与依据，不写"影响较小"；
- 审批结论只有"批准/有条件批准/驳回"三种，有条件批准要写清条件；
- 验证记录写验证人、验证方式、验证结果。

---

## ⑬ 风险登记册（RSK-REG）

**目的**：执行期的风险台账，逐条跟踪状态直到关闭。
**必备表格**：风险清单（编号/描述/类别/概率/影响/等级/应对/责任人/期限/状态）、状态统计表。

```
1 说明
  1.1 编制目的
  1.2 使用方法
  1.3 更新频率
2 风险清单
3 风险状态与趋势
  3.1 状态统计
  3.2 趋势分析
4 已关闭风险
5 新增与升级风险
附录 A 待确认事项
```

**要点**

- 每条风险有唯一编号，描述写"原因→事件→后果"三段式，例如"因第三方接口未按期提供，导致联调延期两周"；
- 概率、影响、等级与《风险管理计划》的定义保持一致；
- 关闭风险写关闭依据与关闭日期，不直接删除；
- 升级风险标注升级对象与升级时间。

## ⑭ 测试报告（TST-RPT）

**目的**：用数据说明测试做了什么、结果如何、能否交付。
**必备表格**：环境配置表、用例执行统计表、缺陷统计表、遗留缺陷表、结论对照表。

```
1 概述
  1.1 编写目的
  1.2 测试对象与范围
  1.3 参考资料
2 测试环境
  2.1 环境配置
  2.2 测试数据
  2.3 测试工具
3 测试执行情况
  3.1 用例执行统计
  3.2 测试类型覆盖
  3.3 计划与实际对比
4 缺陷统计与分析
  4.1 缺陷分布
  4.2 缺陷趋势
  4.3 遗留缺陷
5 测试结论
  5.1 准出准则达成情况
  5.2 风险与建议
6 附件
  6.1 用例执行记录
  6.2 缺陷清单
附录 A 待确认事项
```

**要点**

- 用例执行率、通过率、缺陷密度都要给分子分母；
- 遗留缺陷逐条给等级、影响范围、规避方案、计划修复版本；
- 结论对照《测试计划》的准出准则逐条判定"达成/未达成"，不笼统写"基本通过"；
- 测试环境与生产环境的差异要写明，这是结论可信度的前提。

---

## ⑮ 部署上线方案（OPS-REL）

**目的**：把上线做成可执行、可回滚、有人值守的操作过程。
**必备表格**：版本清单、节点与端口表、部署步骤表、回滚检查表、值守联系表。

```
1 概述
  1.1 目的
  1.2 上线范围
  1.3 上线时间窗
2 环境与依赖
  2.1 目标环境
  2.2 依赖系统
  2.3 版本清单
3 部署架构
  3.1 部署拓扑
  3.2 节点与端口
4 部署步骤
  4.1 前置检查
  4.2 部署流程
  4.3 配置项变更
5 数据迁移
  5.1 迁移范围
  5.2 迁移步骤
  5.3 数据校验
6 回滚方案
  6.1 回滚触发条件
  6.2 回滚步骤
  6.3 回滚验证
7 验证与确认
  7.1 冒烟用例
  7.2 确认人与确认方式
8 应急与值守
  8.1 值守安排
  8.2 应急联系人
  8.3 故障升级路径
附录 A 待确认事项
```

**要点**

- 部署步骤按"操作人、命令/操作、预期结果、失败处置"四列写，可被他人照做；
- 回滚触发条件量化（错误率、超时率、核心功能不可用），不写"视情况回滚"；
- 数据迁移必须有校验方法与回退手段，涉及生产数据要写备份位置；
- 上线时间窗写清开始、冻结、回滚截止、验证完成四个时点。
