# 收尾阶段文档骨架

本文件给出 ⑯–⑱ 的章节骨架。收尾文档的共同要求：一切结论都能追到证据（测试记录、验收检查表、合同条款），不写"项目圆满完成"这类无依据的判断。

---

## ⑯ 用户手册（DOC-UM）

**目的**：让最终用户不看培训也能完成操作。
**必备表格**：环境要求表、权限说明表、常见问题表。

```
1 概述
  1.1 编写目的
  1.2 读者对象
  1.3 术语与缩略语
2 运行环境
  2.1 客户端要求
  2.2 网络要求
  2.3 账号与权限
3 快速开始
  3.1 登录
  3.2 界面导览
  3.3 退出
4 功能操作说明
  4.x 模块名称（每个模块一节，按此结构重复）
    功能说明 / 操作步骤 / 界面说明 / 注意事项
5 常见问题
6 附录
  6.1 术语表
  6.2 快捷键
  6.3 支持与联系方式
```

**要点**

- 操作步骤用"① 点击×× → ② 填写×× → ③ 提交"的命令式，一步一个动作；
- 每个功能配一张界面截图并标注图号，截图要打码真实数据；
- 权限差异用表格说明"角色—可见菜单—可执行操作"；
- 面向最终用户，不出现数据库、接口、表名等技术词。

**常见缺陷**：写成功能清单；步骤跨度过大；截图过期与界面不符。

---

## ⑰ 验收报告（ACC-RPT）

**目的**：对照合同与验收标准，给出可签字确认的验收结论。
**必备表格**：验收依据清单、验收检查表、问题整改表、签字确认表。

```
1 概述
  1.1 验收背景
  1.2 验收依据
  1.3 验收范围
2 验收组织
  2.1 验收小组构成
  2.2 职责分工
3 验收内容与方式
  3.1 功能验收
  3.2 性能验收
  3.3 文档验收
  3.4 安全验收
4 验收过程
  4.1 时间安排
  4.2 测试与检查方法
  4.3 问题处理过程
5 验收结果
  5.1 各项达成情况
  5.2 遗留问题与整改计划
  5.3 验收结论
6 签字确认
附录 A 验收检查表
附录 B 待确认事项
```

**要点**

- 验收依据逐条引用（合同条款号、需求编号、测试报告编号），不写"按合同要求"；
- 达成情况用"符合/基本符合/不符合"三档并给证据编号；
- 验收结论只能由验收小组给出；代理只写"建议结论：通过/有条件通过/不通过"，并注明待签字；
- 签字栏留空，由真实人员签署；不得预填姓名与日期。

**常见缺陷**：验收范围与合同不一致；遗留问题无整改期限；结论早于证据。

## ⑱ 项目总结报告（CLS-RPT）

**目的**：复盘目标达成、过程管理与经验教训，为后续项目提供依据。
**必备表格**：目标达成对照表、进度成本偏差表、质量指标表、经验教训表。

```
1 项目概述
  1.1 项目基本情况
  1.2 建设内容
  1.3 项目周期
2 目标达成情况
  2.1 建设目标对照
  2.2 交付成果
  2.3 验收结果
3 进度与成本
  3.1 计划与实际对比
  3.2 偏差分析
4 质量情况
  4.1 质量指标达成
  4.2 缺陷与返工
5 过程管理
  5.1 计划执行
  5.2 变更情况
  5.3 风险情况
6 经验与教训
  6.1 成功经验
  6.2 问题与教训
7 后续建议
  7.1 运维建议
  7.2 优化方向
8 附件
```

**要点**

- 目标达成逐条对照立项/合同目标，用数据说话（"并发 600，达成 ≥500 的目标"）；
- 偏差分析写原因分类（需求变更、资源不足、外部依赖、估算偏差），不写"客观原因"；
- 经验教训要具体到做法（"需求评审引入业务方签字，减少后期变更 3 次"）；
- 后续建议分"必须做"与"建议做"，给责任方与时间。

**常见缺陷**：通篇表扬；教训写成"沟通不够"；建议无责任方。
